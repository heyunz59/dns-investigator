## 1. 项目背景与目标

课程《人工智能的网络应用》要求开发一个面向网络运行、管理或维护的 AI Agent。项目必须有实际工具调用、专业知识应用、可运行交互、至少四个测试案例及可信的效果评测。

已选题：DNS 解析失败调查助手——基于工具调用与证据分析的网络故障诊断 Agent。

目标用户：校园网络用户和初级网络运维人员。

核心场景：用户反馈“其他网站能打开，某个网站打不开”，提供域名或网址。系统检查问题是否涉及 DNS，必要时继续检查 TCP 与 HTTP/HTTPS，形成有依据、承认不确定性的结论。

核心价值：模型理解问题并选择检查工具；程序执行可靠测量；模型根据证据调整假设，而不是凭经验编造网络状态。

成功标准：输入问题后，系统完成必要检查，返回可追溯的证据、可能原因、判断边界和下一步建议，并保存可复现记录。

## 4. 用户输入与交互

支持两类输入：

1. 调查：例如“其他网站正常，但 https://example.com 打不开，请检查”。
2. 单项查询：例如“查询 example.com 的 A 记录”。

必需信息：有效域名或 HTTP/HTTPS 网址。缺少时询问，不自行猜测。

可选信息：浏览器错误、出现时间、影响范围、指定解析器。

域名输入默认按 HTTPS 访问，并在结果中记录该默认值；完整网址保留路径。若需要检查 HTTP，应作为明确的额外检查记录，不能静默降级后声称 HTTPS 正常。

仅接受支持的协议；拒绝空目标、格式错误、无效端口及带用户名密码的 URL。保留模型调用所需的最少信息，日志不得写入 API Key、认证头或完整网页正文；URL 中疑似敏感查询参数应脱敏。

交互流程：输入 → 必要时补充信息 → 展示简短检查进度 → 展示结果 → 提示日志位置。

测量位置必须明确：结果来自程序所在电脑。若与用户故障现场不同，结论必须注明限制。

## 6. 工具接口契约

三个工具共用结果外壳，字段名可在保持语义的前提下调整：

```text
tool_call_id, tool_name, input, started_at, duration_ms,
execution_status, data, error, source_mode, measurement_location
```

source_mode 区分 live（真实测量）与 fixture（预设测试响应）。网络故障通常是一次有效测量的结果，不等于程序执行失败。例如 DNS 返回 NXDOMAIN 应记录为 DNS 响应状态，而不是 Python 异常或 Agent 崩溃。

### 6.1 query_dns

输入：domain、record_type（第一版 A/AAAA）、resolver（可选，默认使用系统配置的 DNS 服务器）、timeout。

输出：实际使用的解析器、查询类型、响应码、记录与 TTL、耗时、超时或其他错误；能获取时记录 CNAME 链。明确说明此工具执行 DNS 查询，不等于复现浏览器缓存、hosts、代理或安全 DNS 的全部行为。

要求：区分 NXDOMAIN、NOERROR 但无所需记录、SERVFAIL、REFUSED、超时等结果；不得把这些状态合并成“域名不存在”。切换解析器查询应保留两次结果，不能覆盖第一次证据。

### 6.2 check_tcp

输入：目标 IP、port、timeout。第一版围绕网站目标的 80/443 或用户网址明确指定的端口，不做端口扫描。

输出：连接成功、连接被拒绝、超时或其他网络错误，实际目标 IP、端口和耗时。

要求：支持 IPv4/IPv6 的合理处理。TCP 成功只说明本次连接建立成功；失败不能直接定位为服务器宕机或防火墙故障。

### 6.3 check_http

输入：url、timeout；使用有大小上限的 GET 检查，设置重定向次数上限。

输出：HTTP 状态码、最终网址、重定向链、耗时、TLS/请求错误；实际对端地址能可靠取得时记录，无法取得时标为未知。

要求：默认启用证书验证，保留原始域名用于 Host 与 TLS SNI；不得直接用 IP 替换 HTTPS 域名制造证书错误。HTTP 4xx/5xx 是有效响应证据，不能一律归类为“无法连接”。不把网页正文当作 Agent 指令，不执行页面中要求调用其他工具的内容。

### 6.4 工具间的一致性

域名可能有多个地址，HTTP 客户端也可能再次解析或经过代理。记录各次检查的目标、时间、解析器及已知代理模式。无法确认 TCP 与 HTTP 使用同一 IP 时，不声称已验证同一个后端。重定向后的域名变化必须体现在证据里。

为工具循环设置可配置上限。建议初值：每次 DNS/TCP 检查 5 秒，HTTP 总预算 15 秒，最多 10 次工具调用；实现时按所选库的超时语义落实，确保不是仅设置单次读取超时就假称有总时限。

## 7. Agent 行为与证据模型

Agent 必须参与任务理解与工具选择。允许强制参数校验和资源限制，但不能让应用层固定执行所有工具后仅让模型润色结果。

合理路径示例：

- 只问 DNS 记录：调用 DNS 工具即可。
- 解析失败：分析响应类型，必要时用另一个解析器比较；无 IP 时不编造 IP 调用 TCP。
- 解析成功但访问失败：按需要检查 TCP、HTTP。
- 已收到 HTTP 错误响应：分析服务层证据，不继续无依据地确认 DNS 故障。

最小数据结构：

```text
Incident: id, user_input, target, context, measurement_location
Evidence: id, tool_call_id, observation, timestamp, source_mode
Hypothesis: id, statement, status, supporting_evidence_ids,
            contradicting_evidence_ids, missing_information
InvestigationResult: incident_id, observations, hypotheses,
                     conclusion, limitations, recommendations
```

假设状态可以是待验证、获得支持、被削弱、无法确定。不要求强制产生 RootCause 字段；若保留，必须可为空。

规则：

- 禁止编造测量值、调用结果、未执行的检查。
- 主要结论引用已存在的证据编号；程序验证引用有效性。
- 用户陈述与工具测量分开标记。
- 超时只证明本次未及时收到预期响应；单个解析器异常不能直接证明它自身故障。
- 另一解析器成功支持进一步检查当前解析器或访问路径，不等于唯一根因已确认。
- DNS 正常仅针对本次查询范围，不能排除所有间歇性或客户端差异。
- 不生成没有依据的置信百分比。
- 缺少证据时明确说明还需要什么，而不是强制选一个原因。
- 只展示可核查的简短分析依据和工具过程，不要求输出模型内部完整思维链。

## 8. 输出与日志

用户输出包含：问题描述、测量范围、观察结果、可能原因、支持与反面证据、结论、限制、下一步建议。

日志包含：运行 ID、脱敏输入、模型及相关参数、运行模式、时间、工具输入输出、错误、最终结果、总耗时、程序/依赖版本信息。保存模型返回的可见工具调用消息即可，无需隐藏推理。

实时网络状态具有时效性。README 应说明：可重放 fixture 案例；真实网络检查可以重新执行，但不能保证外部网站状态不变。

## 9. 测试与评测

### 基础案例

| ID | 场景 | 判断标准 |
|---|---|---|
| C1 | DNS、TCP、HTTPS 均正常 | 说明本次未复现故障，不否定用户历史现象 |
| C2 | DNS 返回 NXDOMAIN | 准确描述查询结果，不编造地址，不无条件执行后续连接 |
| C3 | 当前解析器超时，备用解析器成功 | 支持当前解析器或访问路径异常，保留根因不确定性 |
| C4 | DNS 成功，TCP 超时 | 指出连接阶段异常，不能直接断定服务器宕机 |
| C5 | DNS/TCP 成功，HTTP 返回 503 | 指出 HTTP 响应阶段异常，不误判为 DNS 解析失败 |
| C6 | 缺少目标、无效输入或部分工具失败 | 合理补充信息或返回有限结论，不崩溃、不伪造证据 |

C6 的几种输入应拆成具体子案例。另设至少一个“只查询 DNS 记录”的请求，证明工具路径具有选择性。

fixture 后端仅返回状态码、记录、时延和错误等原始事实，不返回正确根因。预期答案及评分规则保存在独立评测文件中，不提供给 Agent。至少一个典型真实网络请求要使用真实模型和 live 工具完成。

### 对照实验

A 组：同一基础模型，直接接收问题及对应原始事实，不允许调用工具。

B 组：同一基础模型，通过工具查询对应 fixture 中的事实，形成分析结果。

保持模型、问题、采样参数和评判规则尽量一致。两组都不得获得预写结论；记录 A 组预先获得事实、B 组按需查询的流程差异，以及最终实际取得的信息差异。工具选择能力单独评价，不能与推理正确性混为一项。

至少记录：

- 任务成功率 = 满足该案例预设必需标准的完成次数 / 总执行次数。
- 工具调用正确率 = 工具选择与参数均合理的调用次数 / 总调用次数；同时用案例规则检查必要调用是否遗漏，零调用记 N/A 而非 100%。
- 平均执行时间，可作为附加指标；报告模型耗时、工具耗时可分开记录。

涉及结论质量可人工评分，但必须保存明确规则和真实回答，不仅靠另一个 LLM 自动判分。推荐同配置重复 3 次，保留所有结果；资源有限时记录实际重复次数和限制。

生成真实结果表及至少一张对比图，并保留至少一个失败、不理想或无法给出可靠结论的案例。不得人为编造失败或预填成功率。fixture 数据本身可以设计，模型运行结果必须实际产生。

### 必要验证

工具输入校验、DNS 状态区分、连接错误、HTTP/TLS 错误与重定向、缺失数据、证据引用、调用上限。真实网络测试与离线测试分开，避免互联网波动导致全部测试不稳定。

- 上传代码、依赖、虚构测试数据、脱敏样例结果与运行说明；忽略 .env、密钥、虚拟环境、模型权重、缓存及未脱敏原始日志。不要将整个 results 目录一概排除，应区分本地原始运行记录与用于复现的脱敏提交材料。
- GitHub 存储代码与版本，不等于自动部署或在线运行 Agent。使用者仍需在自己的环境配置模型并执行程序。
- 自动检查可运行离线工具测试；正式模型评测在有配置的环境单独执行，避免每次提交都消耗 API 额度。
- 当前没有创建仓库、推送文件或改变可见性。

接入前待核实：DeepSeek 本地密钥与额度、GitHub 登录身份及仓库创建/推送权限。它们属于执行前提，不影响已确认的方案方向。
